# Profile Narrative Consolidation And Guided Alignment - Phase 24

## Product Goal

Phase 24 makes the loaded profile answer clearer before showing every analytical layer. The profile now uses a three-layer model:

1. **The answer** - one top-level record summary.
2. **The explanation** - compact reviewed issue patterns and concrete guided preference prompts.
3. **The proof** - full evidence, source links, official titles, caveats, procedural context, and methodology behind disclosure controls.

The change is frontend-only plus deployment-drift automation. It does not write production data, change counting logic, change readiness thresholds, or change alignment semantics.

## Prior Hierarchy

The Phase 23 profile still had overlapping layers:

- Quick Read
- issue evidence introduction
- readiness groups
- reviewed issue patterns
- grouped evidence preview
- issue overview
- issue-level "what happened / pattern / voter read" copy
- selected issue records
- comparison

Phase 24 consolidates the first-answer layer into `Record Summary`, moves reviewed issue patterns into that block, and leaves detailed issue evidence behind inspection/expansion.

## Narrative Summary Rules

The new summary is generated by `frontend/lib/profileNarrative.mjs` from existing read API fields:

- interpreted support count
- interpreted opposition count
- interpreted other count
- recorded vote count
- readiness label
- chamber and party metadata

Allowed summary claims:

- strongest reviewed issue pattern
- mixed but interpretable areas
- limited or not-ready areas
- evidence volume
- chamber/party context as orientation only

Forbidden summary claims:

- motive
- ideology labels
- character judgment
- corruption
- voting recommendation
- claims beyond the reviewed sample

## Reviewed Issue Patterns

Reviewed issue patterns now appear inside the top record summary. Each pattern row shows:

- issue name
- support/opposition counts
- readiness-derived pattern label
- concise policy theme
- click target for evidence inspection

The separate lower `Reviewed issue patterns` card block was removed to avoid repeating the same analytical layer.

## Guided Preference Prompts

The issue-preference panel now asks concrete questions about reviewed measures rather than broad "for/against issue domain" questions.

Prompt options:

- I generally favored these measures.
- I generally favored opposing them.
- My views differ by measure.
- I am not sure.

Only the first two options map to the existing alignment endpoint:

- `support_more_action`
- `oppose_more_action`

`views_differ` and `not_sure` do not call alignment and do not create labels. They are UI states only.

Sparse or limited issue areas with fewer than three reviewed Yes/No meanings do not receive a confident prompt. They remain inspectable, but the UI says there is not enough reviewed Yes/No vote meaning for a safe alignment prompt.

## Alignment Behavior

The descriptive record summary stays unchanged by user preference. Personalized alignment appears only after a concrete directional preference is selected.

The implementation filters guided preferences before calling alignment:

- `AlignmentPanel` sends only directional choices.
- `ComparisonPanel` sends only directional choices.
- Non-directional guided choices are excluded from alignment API calls.

This preserves existing alignment semantics.

## Deployment Drift Protection

Added `.github/workflows/render-backend-smoke.yml`.

Behavior:

- runs on `main` pushes touching `backend/**`
- triggers `secrets.RENDER_DEPLOY_HOOK_URL` if configured
- smoke-checks `/health`
- verifies Valerie `/positions` includes `interpreted_total`
- verifies Valerie evidence includes `interpretation_status`

One-time setup required:

- add `RENDER_DEPLOY_HOOK_URL` as a GitHub repository secret
- optionally set `RENDER_API_BASE_URL` as a GitHub repository variable if the backend URL changes

No deploy hook or secret is stored in the repository.

## Known Limitations

- The top-level party context remains cautious and descriptive. It does not compute a party-alignment percentage.
- Concrete prompts are domain/theme based from reviewed issue patterns, not individualized per every measure yet.
- Comparison remains secondary and broad; future work should prefer measure-level comparison when common roll calls are available.

## Next Recommended Milestone

Run a focused measure-level guided alignment pass:

- generate prompts from actual opened issue evidence groups;
- let `views differ by measure` expand into per-measure choices;
- keep the existing deterministic alignment endpoint unchanged until a measure-specific alignment contract is designed.
